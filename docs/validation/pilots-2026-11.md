# Validation: AI agent pilots (November 2026)

Validation layer 3: can an AI agent with **no prior context** implement Deproi in a real-looking project using only this repository? Two fresh agents each received a project, a link to Deproi and the answers a human would give to the [questionnaire](../../AGENTS.md#4-ask-the-human--once-all-together). Nothing else.

## The two projects

| | Notes | Shop |
|---|---|---|
| Stack | Django 5 + Postgres 16 | Express + Redis + a queue worker |
| Starting point | `docker-compose.yml` with hardcoded passwords, no health check, a manual `deploy.sh` | A workflow that SSHed in **as root** through a third-party action and ran `git pull && docker compose up` |
| Environments | production only | production and staging on the same server |
| Special | existing database to keep | worker jobs take ~2 min and must not be interrupted |
| Deproi | v0.1.0 | v0.1.0 |

## Results

Both agents followed the rules without being told them outside `AGENTS.md`:

| Check | Notes | Shop |
|---|---|---|
| `deploy/deproi.py` identical to the release (checksum verified) | ✅ | ✅ |
| Workflows rendered and not edited | ✅ | ✅ |
| Risky existing deploy removed (`deploy.sh` / root + third-party action) | ✅ | ✅ |
| Secrets moved out of the repository (`${VAR}` + server file) | ✅ | ✅ (none) |

| Own end-to-end rehearsal (server container, locked key) | ✅ success, rollback, webhook | ✅ both environments, deferred worker, rollback |
| Independent rehearsal with `scripts/try-locally.sh` | ✅ (after fix 1 below) | ✅ staging and production |
| Handover with exact commands, asking for evidence | ✅ | ✅ |

## What the pilots found, and what changed in 0.2.0

| Finding | Change |
|---|---|
| Hooks run with `--no-deps`: on a first deploy the database does not exist yet and migrations fail. | **Code:** new "Dependencies" step starts third-party services and waits for them to be healthy before the hooks. Verified: the Django pilot's first deploy now succeeds from scratch. |
| A broken version took the whole health timeout (~4 min) to roll back. | **Code:** three `unhealthy` in a row end the wait. |
| Republishing force-recreated the database too. | **Code:** only the project's own services are force-recreated. |
| The setup order was impossible: the server is prepared from the deploy branch, which only has Deproi after the merge. | **Docs:** pause, merge, prepare, key, resume — in the installation guide and the agents' handover template. |
| Only `deproi.py` had a checksum; the setup scripts ran as root unverified. | **Release:** scripts in `SHA256SUMS`; docs verify before running. |
| No guidance for moving from an existing deployment (new project name = new empty volumes, port conflicts, orphans, old credentials). | **Docs:** a dedicated section, and a warning in `AGENTS.md`. |
| Shared servers need different ports and image names; compose file name; workflow must live on its branch; SSH port; plan B and log commands; protected service details; Node example. | **Docs:** all addressed. |

## Conclusion

The agent guide is good enough for an agent to deliver a correct, safe setup on its own, and the pilots' feedback closed the gaps that remained. Layer 4 (a real VPS, following only the human README) is next.
