# Validação: pilotos com agentes de IA (novembro de 2026)

Camada 3 da validação: um agente de IA **sem nenhum contexto prévio** consegue implantar o Deproi num projeto realista usando só este repositório? Dois agentes novos receberam cada um um projeto, o link do Deproi e as respostas que um humano daria ao [questionário](../../AGENTS.pt-BR.md#4-pergunte-ao-humano--uma-vez-tudo-junto). Mais nada.

## Os dois projetos

| | Notes | Shop |
|---|---|---|
| Stack | Django 5 + Postgres 16 | Express + Redis + um worker de fila |
| Ponto de partida | `docker-compose.yml` com senhas no arquivo, sem healthcheck, um `deploy.sh` manual | Um workflow que entrava **como root** por SSH via action de terceiros e rodava `git pull && docker compose up` |
| Ambientes | só produção | produção e staging no mesmo servidor |
| Particularidade | banco existente a preservar | os jobs do worker levam ~2 min e não podem ser interrompidos |
| Deproi | v0.1.0 | v0.1.0 |

## Resultados

Os dois agentes seguiram as regras sem que ninguém as dissesse fora do `AGENTS.md`:

| Conferência | Notes | Shop |
|---|---|---|
| `deploy/deproi.py` idêntico ao da release (checksum conferido) | ✅ | ✅ |
| Workflows renderizados e não editados | ✅ | ✅ |
| Deploy antigo arriscado removido (`deploy.sh` / root + action de terceiros) | ✅ | ✅ |
| Segredos fora do repositório (`${VAR}` + arquivo no servidor) | ✅ | ✅ (não havia) |
| Endpoint de saúde que falha quando uma dependência cai | ✅ `SELECT 1` | ✅ `PING` no Redis |
| Worker protegido com quiesce e parada graciosa | — | ✅ |
| Ensaio de ponta a ponta próprio (contêiner servidor, chave presa) | ✅ sucesso, reversão, webhook | ✅ os dois ambientes, worker adiado, reversão |
| Ensaio independente com `scripts/try-locally.sh` | ✅ (depois da correção 1 abaixo) | ✅ staging e produção |
| Entrega com comandos exatos, pedindo evidências | ✅ | ✅ |

## O que os pilotos encontraram e o que mudou na 0.2.0

| Achado | Mudança |
|---|---|
| Os ganchos rodam com `--no-deps`: no primeiro deploy o banco ainda não existe e a migration falha. | **Código:** novo passo "Dependências" sobe os serviços de terceiros e espera que fiquem saudáveis antes dos ganchos. Conferido: o primeiro deploy do piloto Django agora funciona do zero. |
| Uma versão quebrada levava o timeout inteiro da saúde (~4 min) para ser revertida. | **Código:** três `unhealthy` seguidos encerram a espera. |
| Republicar recriava à força também o banco. | **Código:** só os serviços do próprio projeto são recriados à força. |
| A ordem de instalação era impossível: o servidor é preparado a partir da branch de deploy, que só tem o Deproi depois do merge. | **Docs:** pausar, mergear, preparar, chave, retomar — no guia de instalação e no modelo de entrega dos agentes. |
| Só o `deproi.py` tinha checksum; os scripts de preparação rodavam como root sem conferência. | **Release:** scripts no `SHA256SUMS`; a documentação confere antes de rodar. |
| Nenhuma orientação para migrar de um deploy existente (nome de projeto novo = volumes novos e vazios, conflito de portas, órfãos, credenciais antigas). | **Docs:** uma seção dedicada e um alerta no `AGENTS.md`. |
| Servidores compartilhados precisam de portas e nomes de imagem diferentes; nome do arquivo compose; o workflow precisa estar na branch dele; porta SSH; comandos do plano B e de log; detalhes dos serviços protegidos; exemplo em Node. | **Docs:** tudo tratado. |

## Conclusão

O guia para agentes é bom o bastante para um agente entregar sozinho uma configuração correta e segura, e o feedback dos pilotos fechou as lacunas que restavam. A camada 4 (uma VPS real, seguindo só o README para humanos) é a próxima.
